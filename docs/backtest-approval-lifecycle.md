# Backtest approval lifecycle

A displayed price belongs to one saved source version, full file map and entrypoint, backtest input revision, project object, account/workspace and route visit. Drafts still require explicit Save. Price results and failures cannot replace a later context. Get price cleanup only unlocks its own view/request; it cannot enable a device-local strategy or a newer pending request.

Approval displays the exact nine-decimal nano-USD ceiling with the existing BigInt formatter. Estimates keep four-decimal formatting. The submitted maximum and server pricing are unchanged.

Clicking Approve captures the displayed immutable quote. If navigation or edits occur while its authorization is pending, that explicitly submitted request still proceeds with the original quote ID, maximum, returned authorization ID and `quote-{quote_id}` idempotency key. No new quote is approved, no automatic retry is added, and navigation does not cancel the submitted action. An old completion cannot navigate, overwrite a newer status, unlock a newer approval or leave its newly displayed quote disabled. The resulting balance refresh is scoped to the same account and the initial destination run visit. The shared balance helper also permits only its latest request from the still-current account to publish a value or error, so an older reservation response cannot replace a newer settlement response on the same run. Existing callers need no new argument; an optional predicate adds stricter view ownership.

Unknown/network/5xx failures at authorization or job creation may hide a committed action. If the original quote is still displayed, the UI explicitly says approval or run submission could not be confirmed and offers a manual same-quote retry. A user-initiated retry reuses that exact quote and idempotency key; it does not price or approve current edited inputs. Once either a new job or an existing idempotent job is confirmed, the owning request replaces the obsolete error with “Run confirmed.” before navigating. Stale responses cannot clear or replace newer status. Deterministic 402 remains an insufficient-credit error. A confirmed HTTP 410 at either authorization or job creation clears only that still-current quote and asks for a new price. Generic 409 and other rejected requests retain their actual error and do not imply expiry or clear the quote. A stale 410 cannot clear a newer quote.

## Separate production pay-as-you-go release gate

Edits, navigation, repricing or reload can discard the initial editor flow's in-memory quote/retry context, and a stale completion is deliberately prevented from replacing newer UI. The integrated local #approvals view now discovers the current user's saved authorizations and existing jobs, and permits only explicit original-identity submission while claimable. See approval-discovery-contract.md and approved-submission-recovery-ui.md. A sent request may still finish; navigation is not cancellation. This recovery path is source-tested but has not passed PostgreSQL CI or been deployed.

In this patch's baseline, authorization commits a reservation separately from job creation (`api_jobs.py`, `authorize` and `create_job`). A lost job response can mean a job exists; retrying the same identity is safe because the server locks authorization and enforces one job per authorization plus workspace-scoped idempotency. If the job was never created, however, the reserved authorization has no job to settle: `settlement.py: settle_job` requires a job, and `reaper.py: reap_expired` only scans running jobs with expired worker leases. The original authorization schema has no expiry or release state. A later successful same-quote retry can recover this path, but losing the client context can strand the reservation.

Do not treat this UI work as production financial recovery. The integrated local backend candidate, awaiting database CI, expires unused authorizations 15 minutes after creation. A late unused job claim releases the full reservation with zero charge and returns HTTP 410; reaper-first and repeated expired-unused claims also return 410 without another posting. An idempotent replay of an existing job remains valid even after expiry. That candidate is not enabled production recovery, and no live ledger operation was performed here. Atomic expiry/job-start races and deployed discovery/recovery verification remain release concerns. This UI patch changes no pricing, reservations, settlement, spending limits, server idempotency or backend data.

The phone test assertion now expects the exact displayed maximum; the real phone/browser journey was not run.
